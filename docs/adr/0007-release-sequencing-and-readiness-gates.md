# ADR 0007: Release sequencing and readiness gates

Date: 2026-09-02
Status: Proposed (maintainer ratifies; section 6 collects every ratification item from ADRs 0003–0007 and the six specs)
Resolves: [#17 Define release sequencing and readiness gates](https://github.com/cdowell09/agent-skills/issues/17)
Inputs: [ADR 0001](0001-npx-skills-distribution-contract.md), [ADR 0002](0002-skill-boundaries-and-shared-contracts.md), [ADR 0003](0003-ticket-decomposition-provider.md), [ADR 0004](0004-licensing-attribution-and-contribution.md), [ADR 0005](0005-validation-and-pilot-strategy.md), [ADR 0006](0006-pilot-consumer.md), [Capability configuration](../specs/capability-configuration.md), [Work execution](../specs/work-execution.md), [Human gate](../specs/human-gate.md), [Findings publication](../specs/findings-publication.md), [Dogfooding](../specs/dogfooding.md), [Project research](../specs/project-research.md), [`npx skills` compatibility](../research/2026-07-12-npx-skills-compatibility.md), [Source provenance](../research/2026-07-12-source-provenance.md), the planning map ([#1](https://github.com/cdowell09/agent-skills/issues/1))

Question: Given all resolved architecture, per-skill specifications, licensing, validation, and pilot decisions, what exact incremental release sequence, versioning policy, readiness gate, and implementation handoff should take the catalog from empty repository to its first stable public release?

Skill names used here (`pick-up-work`, `work-the-board`, `pick-up-human-task`, `work-the-human-board`, `dogfood`, `research-project`, `publish-findings`) are working names. Section 4 is the naming pass and proposes the final names.

## Context

The map fixed the publication order: shared contracts; the work-execution pair; the human-gate pair; the `to-issues` disposition (now ADR 0003's ticket-decomposition integration); findings publication; dogfooding and research. ADR 0005 turned that order into waves 0–5 with layers L0–L7 and a gate row per wave; ADR 0006 assigned the same waves to two pilots (5a dogfooding, 5b research) and named its evidence files `0-contracts.md` … `5b-research.md`. Those numbers are load-bearing (release-gate rows, `tests/smoke/results/<wave>/`, pilot file names), so this document keeps them and adds only what neither ADR owns: a scaffold slice before the first contract, a stable release after wave 5, tags and versions, one gate checklist, public names, and the ticket list.

Constraints from every "consequences for #17" section: ship each companion pair together with paired install and update commands and a coordinator preflight (ADR 0001, work execution, human gate); the human-gate pair ships after the work-execution pair because its handoff names that coordinator (human gate); `dogfood` and `research-project` ship with or after `publish-findings`, are presented as complete without it, and research lists the publisher as an optional companion (dogfooding, project research); the README carries the `## External skills` table, the provider install command, the two-file label relationship, and "included here" versus "install separately" (ADR 0003, ADR 0004); `docs/provenance.md` carries the affirmation, the clean-room record with the shingle result, and the `to-issues` history note (ADR 0004, project research); the catalog creates `package.json`, `contracts/`, `scripts/`, `tests/`, and three workflows, and documents `npm test`, Node 22, and the tested `skills` CLI, `gh`, runtime, and `to-tickets` versions (ADR 0005); every wave passes the automated gate and pilot acceptance, and release notes say dogfooding was piloted on one public, unauthenticated web application and name the unpiloted paths (ADR 0005, ADR 0006).

Verified from this session on 2026-09-02: the `skills` CLI hides a skill whose frontmatter has `metadata.internal` strictly equal to boolean `true` unless `INSTALL_INTERNAL_SKILLS=1` is set or the skill is selected by name ([`src/skills.ts`](https://github.com/vercel-labs/skills/blob/main/src/skills.ts)); the reference validator enforces the name and description rules and does not type-check `metadata` values ([`skills-ref` validator](https://github.com/agentskills/agentskills/blob/main/skills-ref/src/skills_ref/validator.py)); the `gh` [v2.94.0 release](https://github.com/cli/cli/releases/tag/v2.94.0) lists `gh issue create --parent` / `--blocked-by` and `gh issue edit --add-sub-issue` / `--add-blocking`, which fixes the floor ADR 0003, ADR 0005, and the capability spec left open. `docs.github.com` and `cli.github.com` remain unreachable from this environment.

## Decision

- **Seven gated releases, ADR 0005's numbering kept.** Wave 0 has two slices: 0a scaffold (`v0.0.0`, no skills) and 0b shared contracts and setup (`v0.0.1`, all seven skills present as internal preflight skeletons). Waves 1–5 ship the skills in the map's order as `v0.1.0` … `v0.5.0`. Wave 6 is the first stable public release, `v1.0.0`, and adds no behavior.
- **Every merge to `main` is installable.** L0–L4 are required on every pull request (ADR 0005). Skills whose wave has not shipped carry `metadata.internal: true`; the installer hides them from `--list` and bare selection, pilots install them by explicit `--skill` selection during their wave, and the wave's release pull request removes the flag.
- **Contracts version independently of the catalog.** Config v1 and the eight contract majors change only additively within the `v1` line; a breaking change bumps that contract's major, updates every consumer in one pull request, and ships a migration section in the generated setup reference. `metadata.version` is descriptive; tags are the only pins the installer understands.
- **One readiness checklist applies to every wave** (section 3), referencing ADR 0005 section 3 for layer sets and ADR 0006 for pilot rows. The two gates never substitute for each other.
- **Names are fixed before wave 0b.** Wave 0b installs skills on both pilots; a later rename breaks `skills-lock.json`, sibling discovery, and every generated `skill:` value. Section 4 proposes: keep `pick-up-work`, `work-the-board`, `dogfood`, `publish-findings`; rename `pick-up-human-task` → `pick-up-decision`, `work-the-human-board` → `work-the-decision-board`, `research-project` → `research-area`. Maintainer ratifies.
- **Implementation is filed by ticket decomposition on this document.** Section 5 lists the slices per wave with ADR 0003 dispositions; the maintainer runs `/to-tickets` on it with the disposition overlay rather than filing from the map.

## 2. Versioning policy

**Tags.** Pre-release tags are `v0.<wave>.<patch>`: `v0.0.0` (0a), `v0.0.1` (0b), `v0.1.0` … `v0.5.0`, then `v1.0.0`; patch increments for any further release inside a wave (a pilot-driven fix, an added half). Every tag runs `release.yml` and the section 3 gate for the waves already released. Tags are immutable pins (`cdowell09/agent-skills#v0.2.0`), opt-in per ADR 0001. After `v1.0.0` the catalog follows semantic versioning as a whole: patch for fixes, minor for a new skill or additive contract change, major only when a released contract major is bumped.

**Default branch.** Unpinned installs track `main`, so `main` carries the same promise as the latest tag: L0–L4 on every merge, and no merge breaks a released contract without the bump procedure below. Unreleased skills live on `main` under `metadata.internal: true`; L0 permits this one boolean in an otherwise string-valued `metadata` map (the installer checks strict `true`; the validator does not type-check); `release-gate` refuses a tag whose wave scope still contains an internal skill or that removes the flag outside the wave scope; L4 keeps the case "explicitly selected internal skill installs and updates".

**Per-skill `metadata.version`.** Descriptive semver: `0.1.0` when a skill's wave ships; patch for prose fixes, minor for added behavior or an additive contract field; a contract major bump forces at least a minor bump in every consumer. At `v1.0.0` every public skill is set to `1.0.0` once; afterwards skills move independently. `release-gate` already checks the values against the release pull request.

**Contract majors.** `config`, `claim`, `receipt.work`, `receipt.human`, `receipt.dogfood`, `receipt.research`, `findings`, `publication` are integers in `contracts/manifest.yaml`; every skill lists the majors it embeds in `metadata.contracts` and its generated `references/protocol-contracts.md`; L2 fails on any disagreement.

**Compatibility promise for `v1`.** Config v1 and each released contract major change only additively; consumers ignore unknown fields; a coordinator meeting a lower major applies documented upgrade rules and a higher one stops with the paired update command. A breaking change (rename, removal, re-typing, new required key, changed outcome meaning) bumps the major in one pull request that updates the manifest, the source heading, every consumer's `metadata.contracts` and `metadata.version`, adds an L3 fixture for the previous major, and adds a "Migrating from `<contract>` v`<n>`" section to `contracts/setup.md`, so every skill's generated `references/setup.md` walks the user through it (a `config` bump also makes guided setup offer the rewrite). The paired update command is the migration for a pair. The capability spec's open question of folding `findings.persistence.*` and `research.persist` into one key is answered: not in `v1`; it is a rename and therefore a `config` major bump.

**`CHANGELOG.md`.** Root file, one section per tag, newest first, with subsections `Skills` (per skill: version, one line per change), `Contracts` (majors as of the tag; additive changes), `Catalog` (docs, CI, tooling), and `Tested with` (the versions, fixture run id, and pilot file paths ADR 0005's `release-gate` writes into release notes; the release notes and the CHANGELOG section are the same text). The release pull request writes the section; there is no "Unreleased" list, because a solo maintainer cuts every release and the log between tags is the source.

## 3. Readiness gate (one checklist per wave)

Applied verbatim in each wave's release pull request; a non-applicable item is marked "n/a: <reason>", never omitted. `release-gate` automates the items marked (A).

1. **Automated layers.** L0–L4 green on the release commit (local L4 on the PR, GitHub source on the tag); the wave's L5 set (ADR 0005 §3) green on the fixture; nightly not red. (A)
2. **Runtime smoke.** `tests/smoke/results/<wave>/` holds a result for every L6 cell the wave needs whose skill hash equals the tagged tree. (A)
3. **Pilot evidence.** `docs/pilots/<repo>/<wave>.md` merged for both pilots with verdict `pass`; every mandatory row passed; every "both" row ran on both runtimes; every finding closed under ADR 0006 rule 5 or deferred with sign-off; hygiene passes over the file with the pilot denylist. (A for presence and verdict)
4. **Second-consumer rule.** Both pilots ran the wave, or the wave file carries a waiver sentence ADR 0006 pre-approved (wave 2 coordinator, wave 3, wave 5a); no other waiver without an ADR 0006 amendment.
5. **Repository-agnostic proof.** Green on the synthetic fixture and pilot-accepted on the pilot whose stack differs from the source project's, or ADR 0005's substitute (primary plus L4 and L6 from the non-Node synthetic consumer) is stated in the wave file.
6. **Provenance.** `LICENSE`; affirmation in `docs/provenance.md`; `THIRD_PARTY_NOTICES.md` equals the generated union; every `NOTICE.md` matches `metadata.provenance`; class 1 hygiene run recorded; shingle diff recorded against the tagged commit when the wave touches `skills/**`. (A except the shingle record)
7. **Companion-pair rule.** Worker and coordinator ship in the same tag with identical `metadata.contracts`; README shows the paired install and update commands; the coordinator's `compatibility` names its worker; the I6 stop passed for the pair.
8. **Install, update, remove.** For every skill the wave makes public: `--list` shows it; exact selection installs it for `codex` and `claude-code`; `--copy` works; `skills update` from the previous tag lands the change; `skills remove` cleans both agent locations with the project-lock caveat recorded. L4 proves it on the synthetic consumer; the pilot I-rows prove it on real repositories (I1–I6 at wave 0b, re-run for newly public skills at each later wave).
9. **Docs.** README section per shipped skill (purpose, capabilities, keys asked in setup, canonical commands, "included here" versus "install separately"); `## External skills` rows current; CHANGELOG section written; release notes name tested versions, fixture run, pilot files, and unpiloted paths.
10. **Naming and metadata.** Names ratified; `skills-ref validate` passes; `metadata.internal` removed from the wave's skills and present on every unshipped skill; `metadata.version` values equal the release PR. (A)
11. **Tag and announce.** Tag pushed; GitHub release from the CHANGELOG section; announcement per the wave table.

## 4. Public naming pass

**When.** Names are ratified in the section 6 sitting and applied when the skill directories are created in wave 0b. Wave 0b installs every skeleton on both pilots by explicit selection; a rename afterwards changes the installed path, the `skills-lock.json` entry, the `skills update` target, the `name` sibling discovery matches, the generated `skill:` values in claims and receipts, the `compatibility` strings naming workers, the `artifact_id` prefixes, and the handoff command text, and it invalidates the specs' worked short ids and fingerprints. The map's suggestion to rename before the second wave is too late once wave 0 has pilots.

**Constraints checked.** Agent Skills naming: lowercase kebab-case, at most 64 characters, equal to the directory; description at most 1,024 characters. Collision check on 2026-09-02: `mattpocock/skills` engineering skills are `ask-matt`, `code-review`, `codebase-design`, `diagnosing-bugs`, `domain-modeling`, `grill-with-docs`, `implement`, `improve-codebase-architecture`, `prototype`, `research`, `resolving-merge-conflicts`, `setup-matt-pocock-skills`, `tdd`, `to-spec`, `to-tickets`, `triage`, `wayfinder`, `wizard` (its other categories were not enumerable from this session); `obra/superpowers` skills are `brainstorming`, `dispatching-parallel-agents`, `executing-plans`, `finishing-a-development-branch`, `receiving-code-review`, `requesting-code-review`, `subagent-driven-development`, `systematic-debugging`, `test-driven-development`, `using-git-worktrees`, `using-superpowers`, `verification-before-completion`, `writing-plans`, `writing-skills`. ## 5. Implementation handoff

**Method.** The maintainer runs `/to-tickets` on this section under ADR 0003's overlay, with a new plan issue quoting section 1 as the parent, not the map. One ticket per row below, split only where the run judges a row exceeds one context window (upstream's sizing rule, [`to-tickets`](https://github.com/mattpocock/skills/blob/6654f6b60cd9d5be8b54c6fafe44346dabeb3b76/skills/engineering/to-tickets/SKILL.md)); every ticket a native sub-issue of its wave's parent; every "blocked by" a native blocked-by edge; dispositions map to `ready-for-agent`, `needs-decision`, `ready-for-human`, so the `needs-decision` label must exist on this repository first (W0a-02). Until wave 1 ships, agent-doable tickets are run by an agent session by hand; from wave 2 the catalog runs its own pairs on this repository (a third consumer, not a pilot, without evidence obligations). Every ticket includes its tests at the lowest applicable layer, passes `npm test`, and regenerates rather than hand-copies any generated reference.

Disposition: A = `agent-doable`, D = `human-decision`, H = `human-execution`; "A then H" means an agent prepares and a human runs or tags.

## 7. Risks to the schedule

- **Installer changes upstream.** The CLI raised its Node floor from 18 to 22.20 between the research revision and ADR 0005, and `metadata.internal`, `--list`, and the lock-file behavior are implementation details, not specification. Mitigation: L4 pins the CLI, encodes the observed internal-skill and project-lock behavior, and fails loudly on a change; if the internal mechanism breaks, unreleased skills move to a `next` branch merged at release, which costs the always-installable `main` nothing.
- **`gh` version floor.** 2.94.0 is verified from the release page, but `gh issue view --json` dependency fields are not. Mitigation: the transport probe order and the shim's REST fallback; the Tier 1 check reports until the fixture confirms.
- **Egress-blocked hosts.** `docs.github.com`, `cli.github.com`, the primary pilot's deployment host, and the standards hosts in the research example were unreachable from drafting sessions. Mitigation: the external link check is nightly and non-blocking; W5-03 verifies from a runner; release notes say which citations were verified.
- **Pilot and maintainer availability.** One person runs every interactive L6 cell and pilot row on two repositories and two runtimes; waves 1, 2, 4, and 5 each need a sitting of hours. Mitigation: unattended rows in remote sessions, waves ordered so each sitting reuses the previous state, and no dates: the schedule is gated, not dated.
- **Runtime unknowns.** Codex implicit invocation (D3), browser provider availability for 5a, PR-event subscription on one runtime only. Mitigation: every gap has a specified fallback and a disclosed downgrade; a wrong fallback is a catalog bug fixed before the wave ships.
- **Upstream `to-tickets` drift** triggers the fallback extension after two consecutive rewordings (ADR 0003). Mitigation: the tested revision is recorded per release; the extension is a pre-specified ticket.
- **Human-only prerequisites** (fixture organization, secrets, affirmation, labels) sit on W0a-11's critical path. Mitigation: they are the first two tickets and need one sitting.

## Alternatives considered

- **Big-bang release after every pilot passes.** Rejected: it defers the first installable artifact by five waves, hides installer and contract problems until the largest surface exists, and contradicts the map's order and ADR 0005's per-wave gates.
- **Per-skill independent releases without waves.** Rejected: pairs must ship together (ADR 0001), the human-gate handoff names the agent coordinator, the producers need the publisher's contract, and shared contracts change all seven at once; independent cadences multiply the `metadata.contracts` combinations the L2 pair test exists to prevent.
- **Tag-only installs.** Rejected: ADR 0001 makes default-branch tracking canonical so `skills update` works; the cost, the always-installable rule, is already paid by L0–L4 on every merge.
- **A `next` branch instead of `metadata.internal`.** Kept as the fallback only: pilots would install from a non-default ref, CI would split, and drift between released and unreleased contracts would surface later.
- **Naming pass at `v1.0.0`.** Rejected for the reasons in section 4.
- **Renumbering waves to the map's shape.** Rejected: ADR 0005's gate table and ADR 0006's file names would need amendment for no behavioral gain; 0a/0b and wave 6 add the missing endpoints without touching either.
